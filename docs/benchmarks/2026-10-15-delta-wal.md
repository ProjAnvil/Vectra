## A2 — query p99 while a merge is in flight

Harness: `TestQueryLatencyDuringMerge` (bench/acceptance_test.go) — 100K/1M base, 4 reader goroutines, 12.5 write-batches/s (50 edges each), three phases:

| Phase | bfs p50 | bfs p99 | shortest-path p99 | point p99 |
|---|---|---|---|---|

## A4 — WAL-Off import throughput vs v0.6.0 (rollback line)

`make bench SIZE=medium MODE=engine` (identical harness on both worktrees, back-to-back, same seed/machine):

| | nodes/s | edges/s | Seal |
|---|---|---|---|
| v0.6.0 | 4,684,801 | 4,092,219 | 77.7ms |
| v0.7 (run 1) | 1,075,490 | 408,839 | 530.5ms |
| v0.7 (run 2) | 1,030,896 | 355,781 | 607.9ms |

Regression: **−90.1%** (line: ≤5%). **A4 FAIL — D2 rollback line triggered.**

Root cause (diagnosis only, no remediation per brief): the harness injects with unbatched per-op `AddNode`/`AddEdge`. v0.7's generation model materializes **one immutable micro-layer per unbatched write** (builder build + generation publish), and 1M such layers become garbage that (a) dominates the inject path and (b) keeps GC churning through the subsequent query phase (see A1 note). Context from A5: the same import **batched** (`g.Batch`, 100 edges/batch, WAL off) runs at **9.71M edges/s** — 2.4x v0.6.0's unbatched rate — so the regression is specific to the per-op idiom, not the WAL-off pipeline. The spec's "WAL Off = v0.6 snapshot behavior" promise (§4 R5) holds for durability semantics, not for unbatched per-op throughput.

Options for the D2 decision (not executed here):
1. **Accept + document**: declare `Batch` the bulk-import idiom (README/spec), keep per-op writes as the compatibility path with a documented cost; re-baseline the harness to batched injection for future comparisons.
2. **Optimize in v0.7.x**: absorb unbatched writes into an open builder window (batch-absorption or layer reuse) so per-op cost approaches v0.6's in-place writes.
3. **Rollback** per D2 (revert the delta layer of work), which the other acceptance lines (A1/A3/A5/A7/A8 PASS) argue against.

## A5 — WAL Always + Batch group-commit throughput

`TestWALGroupCommitBatchCost`: direct-mode `g.Batch` of 100 edge upserts per boundary (one frame + one fsync per batch):

| Mode | edges/s | batch-fsync/s |
|---|---|---|
| ModeOff | 9,713,560 | — |
| ModeInterval | 8,628,060 | (no per-batch fsync) |
| ModeAlways | 9,285,540 | 92,855 |

The ≥50K ops/s line assumed production NVMe fsync (0.2-1ms). This machine's APFS `fsync` is not a durable barrier at these latencies (~sub-10µs observed), so the premise does not hold here; the measured numbers are recorded without the gate, per the brief. On storage with true fsync costs, ModeAlways throughput is bounded by `batch_edges / fsync_latency`.

## A6 — merge duration + amortization

`TestMergeAmortization`:

(a) Explicit Seal (full merge pipeline) with a 65,536-edge layer quantum:

| Base | Seal duration |
|---|---|
| 100K nodes / 1M edges | 1.32-1.63s |
| 1M nodes / 10M edges | 6.90-7.07s |

(b) Amortized share over a 50K-edge wrapper workload (1000 × 50-edge changesets, 100K/1M base):

| Regime | wall + final fold | merge overhead share |
|---|---|---|
| zero-merge reference | 1,697ms (fold 1,458ms) | — |
| defaults (64 layers + 64K edges) | 8,767ms + 264ms | **81.2%** |
| volume-bound (layer cap off, 64K-edge interval) | 235ms + 1,311ms | −9.7% (~0) |

**Verdict: the <10% line is missed under spec defaults at the 100K/1M tier (77-81% across runs) and met under the volume-bound regime.** Every fold costs O(base + layers) — the merge re-unions the whole base — so the amortized share is governed by `merge_interval / base_size`: with small (50-edge) changesets the layer cap forces a fold every 3,200 edges against a 1M-edge base. Tuning contract: **size MaxLayers/MergeEdges so the fold interval carries edge volume comparable to the base** (or rely on Close/Seal folds for burst workloads). Partial/incremental merges remain the structural fix (deferred to v0.8, spec §9 R11).

## Hardening retest (2026-10-16)

Task 7 (v0.7 closeout) landed three changes and re-measured the failing lines:
the **direct-mode write absorption window** (unbatched per-op writes accumulate
into one open builder and materialize one layer per flush — read entries,
boundaries, and capacity caps — instead of one layer per op), the
**per-generation View cache** (the three-source traversal/cypher assembly is
built once per published generation, keyed by the genView pointer), and the
**size-proportional merge threshold** (a background fold fires when the
unmerged stack carries `max(MergeEdges, base.EdgeCount)` edges; `MergeEdges`
64K is the floor; `MaxLayers` rises 64 → 2048 as the pure deep-stack stall
backstop).

- vs the **same-session** v0.6.0 run: 0.74x — the reference machine measured v0.6.0 itself 22% hotter this session than during task 6 (5.0M vs 4.09M); the same-session ratio is the stricter reading and is recorded here for honesty. ### Harness notes (recorded per the task brief)

- **A5/A4 harness shape difference**: A4 (`make bench`) injects with valid
  nodes then edges (real record work); the A5 harness (`TestWALGroupCommitBatchCost`)
  upserts edges between nonexistent node keys — those writes fail fast at
  endpoint validation, so A5's absolute rates measure the WAL batch/error
  path, not record throughput (no frames are logged; the "batch-fsync/s"
  column counts batch boundaries). The fsync machinery itself is exercised
  with real frames by A7's crash-recovery test. A4's batched comparison
  (9.71M edges/s in task 6) shares this caveat — do not read it as record
  throughput.
- **One mega-Batch is not the fast path**: a single Batch spanning a whole
  import materializes one giant layer (one BuildWithIDs, one publication) but
  pays the whole-batch tombstone/fold bookkeeping up front and forfeits
  incremental flushes; many small-to-medium batches — or since the hardening
  pass, plain unbatched writes absorbed into ≤64K-edge windows — are the
  intended shapes.
- **A2 dual basis**: the acceptance line reads the idle basis (merge-window
  p99 vs the merged-base floor); the steady basis (merge-window vs
  continuous-writes) is reported alongside because merges are the mechanism
  that bounds the stack the steady state grows.
