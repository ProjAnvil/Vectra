# 瓶颈修复复测报告(B1/B2/B3)

Date: 2026-10-17 · 分支: `feat/perf-bottleneck-fixes`(基于 4ddebc3)
环境: 与基线相同(Apple M5 Pro 18 核 / 64GB / APFS / Go 1.27.2)
对照: `docs/benchmarks/2026-10-16-perf-baseline.md`(同种子、同矩阵、同工具)
Spec: `docs/superpowers/specs/2026-10-16-perf-bottleneck-fixes-design.md`(v4 修订见文末)

## 结论(TL;DR)

1. **B2(读路径分配)全面达标并超预期**:neighbors M-w8 QPS 376K→**7.8M**(20.7×),p50 4.0µs→458ns,p99 250µs→**4.3µs**(58×);L 档 neighbors p50 31.5µs→583ns(54×);path/bfs2 各档 2-4×;读负载 GC CPU 10.5%→**5.4%**(M)、14.7%→6.5%(L)。
2. **B1(持续写入读崩塌)达成验收线**:mixed-read p50 109ms→**微秒级**(见下表),p99 1.42s→数毫秒级;L 档 p99 2.80s→同量级改善。修复分三层:层栈治理(v4)+ 读路径分配削减 + 发布时增量视图预构建(v4-3)。
3. **B3 记录为结构性成本**:未批注注入纯路径 ~2.8M edges/s(pprof:镜像字符串 map + EdgeKey 三串比较占主导),高于 A4 底线 1M/s;镜像整数化入 backlog。
4. **验收门 A2-A7 全绿 + race 干净**;A2 按 v0.7 加固先例重校准(B2 使 idle 地板塌 ~45×,比值线机械破线,新增绝对地板口径)。

## B1:修复栈(自底向上)

| 层 | 内容 | 提交 |
|---|---|---|
| F1 | `delta.FoldLayers`:层栈→单层,保 ID/序/墓碑并集,200 轮随机差分对拍 | b8466eb |
| F2 | 尺寸分层层栈治理:F/T/tail 三段;折叠仅写路径(读触发 flush 只发布);tail 体量门槛 64 边;T≥max(512,F/2) 并入 F(摊还 ≤3 拷贝/记录);体量 Seal 仅 Batch 边界(≥max(64K, base));wrapper 模式整体跳过 | b065665/1101a44/7d22ca9 |
| F3 | 发布时增量视图预构建:读者永远缓存命中;纯追加 O(新增层),T 折叠回卷 F 边界快照(每折叠区间一次 O(F) 拷贝);白盒等价测试钉死与全量重建一致 | c77fa17 |

v1(整栈折叠)被 A3 门抓出两个真缺陷(整栈重折二次方、读路径内联 O(base) Seal),v4 重设计修复——验收门履行了职责。

未竟项的机制:写者被折叠/快照/预构建成本节流(达成 53-56 写/s,供速 200),读 p99 与写路径事件同拍(62ms ≈ 写 p99 68ms)——残余是**写侧摊销**,不是读侧重建(读者已全量缓存命中)。继续压缩需把折叠+预构建移出写者(独立合并 goroutine + 发布协议,即 wrapper 模式思路下沉到 direct 模式)或持久化数据结构消除快照拷贝,均记 v0.8 候选。

## 残余与后续

1. **mixed 写侧摊销(主要未竟项)**:折叠/快照/预构建成本落在写者——达成写速率 53-56/s(供速 200,基线达成 164),读 p99(62ms)与写 p99(68ms)同拍。压缩路径:折叠+预构建移出写者(独立 goroutine + 发布协议)或持久化结构消除 O(F) 快照拷贝,v0.8 候选首位。
2. **B3 结构性**:镜像 map 整数化/分片(写路径 ~2.8M edges/s 的常数),v0.8 backlog。
3. **读 p50 距激进线 1.8-2.6×**:读者已缓存命中,残余为写事件同拍尾部 + GC 流量;随(1)解决。

## v4 设计修订(对 spec 的补充)

- F2 修订:v1"层数阈值整栈折叠 + base/8 体量 Seal"作废——A3 门证明其二次方写成本与读路径 Seal 不可接受。v4:三段尺寸分层、写路径专属触发、tail 体量门槛、max(64K,base) 体量线。
- F3 启用:spec 曾按 YAGNI 推迟增量视图;复测证明必要(层栈变浅不解决记录体量的每发布全量重建),以发布时预构建 + 域分离偷取扩展实现,避免读者竞争。
- 新增:A2 门重校准记录(B2 副作用);差分桩存在性匹配规范(删除键零 ID 假象,非引擎 bug——已在基线 ee256e3 验证)。

# 第二轮(2026-10-17):残余项 1 修复——写侧摊销

分支: `feat/background-folder`(基于 8a0f12c)。同行调研: LevelDB/RocksDB/Pebble/Badger 一致为"写者 O(1) 发布 + 后台压实 + 不可变输入原子安装 + stall 背压";SQLite autocheckpoint 是反例(提交线程做压实,commit 尾部周期性尖峰)。

## 结论

1. **画像推翻了假设**: 写者节流的根因不是折叠(FoldLayers/快照合计 <1% CPU),而是**视图缓存未命中风暴**——单槽缓存在 `view.Store` 之后才填充,读者在窗口内全量重建(`appendLayer` 占全部 CPU 的 63%),且读者的无状态条目覆写写者的增量状态,逼写者也全量重建(10ms/批)。
2. **per-generation 视图槽位**(6e1f577): 槽位挂在 genView 上,写者发布前填好,读者 CAS 只进自己代的空槽。M-w8 读 p50 2.67ms→238µs,p99 66→16ms,写 55→132 批/s。
3. **后台折叠器**(a7db582): 写者只发信号;折叠器从不可变代计算折叠 + 折叠前缀的完整视图状态,经原子交接槽交给写者,写者下次发布时前缀拼接 + O(tail) 追加。发布权只归写者(无 CAS 协议)。写 132→**166 批/s**(= 无折叠基线的步调上限),写 p99 60→**5-6ms**,max 330→15-18ms。

## 终验(engine, 供速 200 批/s × 50 边, M-w8 ×2)

| 指标 | 10-16 基线 | 第一轮末 | **第二轮末** |
|---|---|---|---|
| mixed-read p50 | 109ms | 2.75-3.98ms | **205-212µs**(530×) |
| mixed-read p99 | 1.42s | 62-64ms | **14.6-15.4ms**(95×) |
| mixed-read QPS | 31 | 507 | **4520-4834** |
| mixed-write 达成速率 | 164-167(无折叠) | 53-56 | **166**(步调上限) |
| mixed-write p50 / p99 / max | 151µs / 393µs / 3.9ms | ~1ms / 68ms / 330ms | **851-862µs / 4.8-5.9ms / 15-18ms** |
| 纯读 bfsall p50 / p99 | 3.96 / 13.2ms | 4.49 / 34ms | **3.10 / 7.5ms** |
| 纯读 bfs3 p99 · reach p99 | 3.64 · 3.08ms | 3.68 · 13.1ms | **1.94 · 1.68ms** |

M-w16: 读 p50 248µs / p99 47ms,写 154/s(p99 13ms)。L-w8: 读 p50 **1.30ms** / p99 95ms(基线 149ms / 2.80s),写 120/s(p99 15ms,max 71ms);L 的读 p99 由 bfsall 族本身(p50 56ms 的全图 BFS)主导。

spec 验收线(M-w8): 写达成 ≥190 → 166,**即供速 200 下步调器的实际上限**(无折叠基线同为 164-167,time.Sleep 粒度所限);写 p99 ≤10ms → 4.8-5.9 ✓;写 max ≤50ms → 15-18 ✓;读不回退 ✓;门 A2-A7 + race ✓。

## 残余

- 写 p50 851µs(基线 151µs): 每发布的预构建追加 + NewView 标签/杀除聚合 + 折叠并入;写者 CPU 占比 ~1.4%,非瓶颈。
- 折叠器每次从零构建折叠前缀的视图状态(O(F+T),后台): F 受体量 Seal 界住(≤max(64K, base));长跑下折叠器可能落后 → 1ms slowdown 背压兜底。增量复用 F 的 sources 可再降,v0.8 候选。
- 门卫生: A2/A3 时序线在 -race 下改为只记录(合并前 main 同样失败——race 检测器下时序门无意义,项目约定以非 race 运行为准)。

# 第三轮(2026-10-17):写 p50 减半——杀除集增量聚合

## 画像

写者每批 CPU ≈450µs,其中 prebuildView 345µs;NewView 880ms 累计中 **830ms 在 deadBase 聚合循环**——折叠层 F' 的 base 边杀除列表随墓碑累积(每次 upsert 杀 base 平行边),每发布全量重建 map,313µs/批。

## 修复

`engine.KillSet`:杀除集改 **COW 分块位图**(每块 32K ID,512 词)。`With` 追加只拷触及块,未触及块跨代共享底层数组——增量聚合成本 O(新增杀除 + 块数),与累积量无关。`viewBuild` 携带两套集合并随 `appendLayer` 增量扩展;`NewViewWithKills` 信任调用方集合,跳过全栈重聚合;`NewView`(全量构建路径)内部改为同一 KillSet 聚合。查杀路径 `Rows` 的 map 查找换为块位图探测(两次索引+位运算,同级成本)。COW 共享与追加隔离由单测钉死。

## 结果(M-w8, writerate 200, 10s)

| 指标 | 第二轮末 | **第三轮末** |
|---|---|---|
| mixed-write p50 | 851µs | **401µs**(2.1×;无治理基线 151µs) |
| mixed-write p99 / max | 4.8-5.9ms / 15-18ms | **4.1ms / 11.6ms** |
| mixed-read p50 | 205-212µs | **164-173µs** |
| mixed-read p99 | 14.6-15.4ms | **13.9ms** |
| 写达成速率 | 166 | **173**(步调上限) |
| bfsall p50 / p99(纯读) | 3.10 / 7.5ms | **2.96 / 6.64ms** |

writerate 400 下:写 290/s(p99 5.5ms),读 p50 168µs——供给加倍仍线性吸收。

**A4 导入回归修复(同轮)**: make test 抓到未批注导入 560-780K edges/s(< 1.0M 地板;136f7ff 复测确认第二轮引入)。根因:导入的 64K 边吸收窗口每刀在写者上付 64K 记录的预构建——纯导入无交错读者,纯浪费。修复:`prebuildMaxLayerEdges = 4096`,超限层跳过预构建(读者走槽位 CAS 回退;下一个小发布一次全量重建恢复增量链)。A4 恢复 **1.56M edges/s**;混合负载不受影响(读 p50 179µs / p99 15.5ms)。教训:**发布前预构建的收益以"有读者"为前提**,写侧成本必须按层形分档。

## 残余归因(记录,不修)

- **M-w16 读 p99 44ms**(w8 为 14ms):分配器竞争——16 个并行 BFS worker 的 row 路径(`View.Rows` 每调用新分配 + viewRow 三切片 zip)+ mheap span 锁(画像 41.5s cum)+ 调度器颠簸(usleep 23%/osyield 22%)。在 50ms 线内;修复方向 = row 路径分配消除(v0.8)。
- 写 p50 剩余 250µs(对无治理基线):每发布的 NewViewWithKills 标签表重建 + appendLayer + 块拷贝——读者 164µs p50 的对价。
- 折叠器 CPU 2.7%,其 O(F+T) 从零构建不构成瓶颈——增量复用 F sources 维持 YAGNI。
