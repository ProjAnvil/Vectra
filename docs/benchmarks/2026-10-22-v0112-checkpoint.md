# v0.11.2 checkpoint 实测：从 O(N) 快照到 O(1) manifest 轮转（2026-10-22）

分支 hotfix/0.11.2。v0.11.2 把 checkpoint 从"每次 Seal 写全量快照"（O(N)，
随库线性增长）改为**保留式 WAL 增量链**：轻量档只做 WAL 段轮转 + manifest
v2 改写（O(1)），压缩档按保留字节数阈值触发才写全量。设计定案见计划文档
`docs/superpowers/plans/2026-10-22-v0112-checkpoint.md`（细化并取代
`docs/benchmarks/2026-10-22-v0112-scope.md` 项 4 的 delta-文件草案）。

测量窗口：2026-10-22 23:19-23:50，安静机器独占运行。协议与
`2026-10-21-wrapper-checkpoint-cadence.md` 相同：`writer.Attach` + `Submit`
组提交，8192 向量 × 768 维，seal 停顿归因于跨 seal 边界的下一个 Submit 排队
等待。

## 设计摘要（详见计划文档）

- **保留式 WAL 链**：轻量档 = `wal.Rotate()`（新段、保留旧段）+ manifest
  v2 `RetainFrom` 指向链首；恢复 = base + 从 RetainFrom 起的段链重放 + 活动
  尾（重放机制全部现成）。压缩档 = v0.11.1 全量流水线（v6 快照 + Reset 删
  链 + forest），由保留字节数阈值 `DefaultCompactBytes = 256MiB` 触发——界
  住恢复重放量（每保留一字节都是下次 Open 要重放的字节），不是写路径。
- **轻量/压缩分档规则**：血统首次 checkpoint 必走压缩档（RetainFrom 0 是
  v1 哨兵，无链可表达）；base 非 v6 必走压缩档（迁移与绊线 seal 同理）；
  保留字节达阈值、或链首段为 0，强制压缩。
- **v6 绊线**：store 快照版本号 5 → 6（仅版本字节，布局不变）。v0.11.1 及
  更早二进制对 v6 base 硬失败——杜绝"旧读者忽略 RetainFrom、只读 base 丢
  增量"的静默损失面（同 v4/v5 纪律）。
- **陈旧 forest 加载门**：加载门从"forest 必须精确匹配 base"放宽为
  "forest LSN ≥ base LSN 且 CRC/声明匹配"——陈旧 forest 由段链重放窗口
  覆盖（重放幂等靠 State.Add 扫描序去重）；不匹配仍弃用重建。

## 诚实备注

1. **35% 残余 seal 占比**来自段轮转的 manifest fsync + 组提交排队，不是快
   照写；再往下压需要去掉 fsync 或改异步 manifest，属另一个权衡。
2. **首次 checkpoint / 新库 Close 仍走压缩档**（结构性规则，上表 64MiB 行
   的 Close 1.058s 即此），全量写只是从"每次"变成"每 256MiB 保留字节一次"。
3. **陈旧水位快照在两次压缩之间持久保留**（设计使然）：轻量档不删任何段
   与旧快照，磁盘占用在压缩边界才回收；崩溃窗口（新 base 落、manifest 未
   落等）由既有 torn-尾纪律覆盖（task-6 崩溃窗口测试全绿）。
