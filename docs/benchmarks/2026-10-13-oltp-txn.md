# OLTP 事务层基准（2026-10-13，feat/oltp-txn 分支，vectra-bench）

环境：Apple M5 Pro（18 核 CPU）、Go 1.27.2、单进程单节点 raft（bolt 持久化）。
方法：与 2026-10-12 压测同一套设施（幂律 BA 图 + 度加权参数固定化，seed=42，64 个采样热点起点）；
事务负载 `txnsi`/`txnser`（HTTP-only）= "GET /v1/neighbors 取 token 与邻居键 → POST /v1/txn 提交热点起点节点的受控 upsert（SER 附带 4 邻居读集）→ 409 重试≤3 → 成功后按 README 规定的 RYW 礼仪轮询 /v1/stats 至 publishedSeq ≥ index"。
复现：`make bench SIZE=<s> MODE=http WORKERS=<n> WORKLOADS=txnsi,txnser [BENCH_EXTRA='-seal-interval <d>']`。

## 4. 事务负载：SealInterval 旋钮（M 档 10万节点/100万边，8 worker）

严格 RYW 客户端的吞吐上界 = workers / 发布周期（发布周期 ≈ SealInterval + clone+Seal 耗时，
M 档 clone+Seal ≈ 300ms）：

| 配置 | txnsi 提交QPS | 冲突% | p50 |
|---|---|---|---|
| 2s（默认） | 4.8 | 0.0% | 2.29s |
| 1s | 6.4 | 0.0% | 1.29s |
| 250ms | 14.4 | 0.0% | 585ms |
| 250ms × 16 worker | 28.8 | 0.0% | 591ms |
| 250ms × 1 worker | 1.8 | 0.0% | 590ms |

L 档（100万/1000万，2s 默认，8 worker）：1.6 提交/s，p50 ≈ 5-6s（发布周期含 ~3s clone+Seal）——可用但受发布成本支配，与"大图热替换"的既有成本模型一致。

## 5. 关键判读：客户端礼仪决定冲突率

同配置（M、8 worker）下两种客户端行为的对照（bench op 修复前后，数据均为实测）：

| 客户端行为 | txnsi 冲突% | 提交QPS | 机制 |
|---|---|---|---|
| 立即重提交（不等发布） | 93.3% | 31.6 | 读到的发布快照落后于**自己**刚提交的写：64 热点键轮转 × 45ops/s 在 2s 陈旧窗口内覆盖全部键 → 自冲突（单 worker 也 77%） |
| RYW 礼仪（提交后轮询至可见） | 0.0% | 4.8 | 每次写建立在最新已发布状态上；代价是等待一个发布周期 |

结论：高冲突数字是**反模式客户端的自伤**，不是系统缺陷；README 规定的 RYW 礼仪将其归零。
非 RYW 的高吞吐客户端若写分散键（不 revisit 陈旧窗口内的键）也不会触发自冲突——OCC 拒绝的
只是"基于过时快照的写"，行为符合 spec §2.7 的有界陈旧声明。

## 6. 运维指引（写入 README 的口径）

- 交互式事务 + 严格读己之写：吞吐由发布周期支配 → 调低 `SealInterval`（M 档 250ms 时 8/16 worker 分别 14.4/28.8 提交/s）；发布成本随图规模增长（L 档 ~3s/次），大图高频事务需权衡。
- 热点键高并发写（Neo4j 式 "don't block the rock" 场景）：OCC 用 abort 替代阻塞——S 档（即时发布）16 worker 下 SER 也仅 4.3% 冲突；陈旧读 + 密集重写同键是唯一需要避免的组合（§5）。
- 事务验证本身的开销在 fsm 级基准已测（SER16 +4.5~11% ns/op）；HTTP 层的单事务延迟（~20ms）由 2×HTTP + raft 共识主导，与验证无关。
