# Spec: RYW Await — 读己之写长轮询端点（v0.5.0）

> 状态：rev1（依据 TxnGroup Task 0 + 0b 重诊结论，用户 2026-10-14 批准的重定范围）
> 日期：2026-10-14

## 1. 问题与目标

v0.4 的读己之写（RYW）礼仪是**客户端 10ms 轮询** `GET /v1/stats` 直到 `publishedSeq >= commitIndex`。Task 0b 实测（S 档/16w/txnsi）：RYW 等待占 p50 26.5ms 中的 **11.1ms（42%）**——其中约 10ms 是纯轮询量化，~1-3ms 是真实发布滞后（小图 clone+Seal）。

**目标**：服务端长轮询端点，把 RYW 等待压到"发布滞后 + 单次 RTT"（预期 ~2-4ms），S 档 16w txnsi TPS 从 ~580 提升到 ~750-850（受剩余 commit 相位 ~15.6ms 支配，见 §6）。**出范围**：发布路径本身提速（clone/Seal 摊销）；watch/流式推送；fsync 语义。

## 2. 先例

etcd watch（rev/wait 语义）、Kafka consumer 长轮询 fetch、DynamoDB 强一致读的等待语义——共同形态：客户端带序号请求，服务端挂起直到满足或超时，单次 RTT 返回新序号。选长轮询而非流：HTTP 语义简单、无连接状态、与现有 X-Vectra-Snapshot 头协议正交。

## 3. 设计

### 3.1 fsm 发布通知（server/fsm.go）

`fsm` 增加发布通知通道（notify-channel 模式）：

```go
pubNotify atomic.Pointer[chan struct{}] // closed on each publish, then swapped
```

- `newFSM` 初始化；`publishOnce` 在 `published.Store` 成功落位后（pubMu 临界区内）：close 旧通道、存入新通道。版本检查未通过的克隆不通知（没有新 seq 可见）。
- `WaitPublished(ctx, minSeq) uint64`：循环 { seq 双检（快照通道前后各一次，消除竞态窗口）→ 满足即返回；否则 select { <-ch, <-ctx.Done() → 返回当前 seq } }。不持锁等待；Restore 的首次发布同样通知。

### 3.2 HTTP 端点（server/api.go）

```
GET /v1/await?seq=<uint>&timeoutMs=<0..30000，默认 5000>
→ 200 {"publishedSeq": M, "reached": bool}   + X-Vectra-Snapshot: M
```

- `seq` 非法/缺失 → 400 `VALIDATION`；`timeoutMs` 非法 → 400。上限 30s（服务端承诺上限）。
- **不经过 readiness 门**：首发布前等待是合法语义（Restore 首发布携带 seq 会唤醒）；ctx 取 `r.Context()`+timeout，客户端断连即取消。
- 永远 200（超时=未达，`reached:false`，客户端自行决定重发）；不算 query 计数。
- 幂等、只读、任意副本可用（publishedSeq 是本地值——与现有 RYW 轮询同一语义边界：等的是**本副本**的发布）。

### 3.3 客户端礼仪升级（bench + README）

bench `waitForPublish` 改为单次/循环 `await`（每次服务端等 min(剩余, 5s)）；README Retry etiquette：await 为主，轮询保留为 pre-0.5 兼容措辞。

## 4. 测试矩阵

| 类别 | 用例 |
|---|---|
| fsm 单元 | 已满足立即返回；发布唤醒（waiter 挂起→sealNow→返回，确定性断言结果）；ctx 超时返回当前 seq 且不早于超时；通道换新后 waiter 重挂正确（-race） |
| HTTP | seq 已达 → 200 reached=true 即时返回；未达+短 timeoutMs → reached=false 且耗时≥timeout；挂起中后台 Apply → reached=true；坏 seq/坏 timeoutMs → 400；X-Vectra-Snapshot 头与 body 一致 |
| bench | waitForPublish 走 await 后 newTxnOp 行为不变（既有 cap-expiry 测试继续绿） |
| 验收 | S 档/http/16w/txnsi/10s×3 次：rywWait 相位均值 ≤5ms，TPS ≥750；p50 相对 26.5ms 下降 ≥15% |

## 6. 预期与边界

commit 相位（15.6ms = dev 机 fsync ~7ms + 流水线）不因本特性改变——TPS 上限 ≈ 16/(0.65+15.7+3)ms ≈ 820。**进一步提速依赖 Linux 级存储重定基线**（生产 NVMe fsync 0.2-1ms，批周期 ~1-3ms → TPS ~4,000+），这是运维侧动作，不在本 spec 代码范围内；基线数字出来后再评估是否需要任何服务端攒批。
